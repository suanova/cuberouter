# 组织功能一期 PRD

> 本文档定义 CubeRouter 组织能力一期的产品目标、业务范围、角色权限、核心流程、体验要求和验收标准。
>
> 组织功能当前尚未正式上线，因此本文以目标产品语义为准，不承诺兼容当前分支中的中间态组织行为。当前实现可作为交付评估和复用参考，具体落地方式由配套技术方案承接。
>
> 本 PRD 不展开底层实现、接口契约和工程改造方案；这些内容由 `docs/ORGANIZATION_TECHNICAL_DESIGN.md` 承接。

## 1. 背景

当前分支已经具备一版组织功能雏形，包括组织、成员、邀请、组织 Key、组织审计、组织额度、组织日志/任务归属以及部分平台管理入口。

需要注意的是：这部分功能尚未正式上线，尚未形成对线上用户的兼容承诺。因此后续交付应优先保证新版组织能力的产品正确性、体验一致性、安全性和治理闭环。

当前实现整体更接近旧版 workspace 方案，主要差距包括：

- 缺少明确的 owner 角色和所有权治理规则。
- 个人空间与组织空间的切换、回退和请求归属仍需统一。
- 组织计费已有雏形，但完整的预扣、结算、退款、重试和修复闭环仍需补齐。
- 邀请、Key 批量操作、解散组织、审计脱敏等高风险环节仍需加强。

因此，本 PRD 将组织能力重整为“以新版组织语义为目标，结合现有能力分阶段交付”的产品需求。

## 2. 产品目标

### 2.1 核心目标

CubeRouter 需要支持组织作为独立的企业协作和资源治理边界：

- 协作边界：组织成员可以共同管理组织资源。
- 权限边界：不同角色拥有不同管理能力。
- 资源边界：个人 Key、组织 Key、个人日志、组织日志、任务和额度不能串用。
- 计费边界：组织 Key 调用只消耗组织额度和 Key 限额，不影响责任人的个人额度、订阅或余额。
- 审计边界：组织内高风险操作必须可追踪、可回溯、可脱敏展示。
- 平台治理边界：平台 admin/root 可以从管理端处理组织状态、额度、成员、Key 和审计问题。

### 2.2 一期成功标准

一期完成后，应满足：

- 用户可以创建组织，并作为唯一 active owner 管理组织。
- 用户可以在个人空间和组织空间之间切换，普通业务请求带明确 Account Context。
- 组织成员可以通过邀请加入组织。
- 组织成员可以创建和使用组织 API Key。
- 组织 Key Relay 调用只扣组织额度，不扣个人额度。
- 组织 Key、日志、任务、用量、审计按组织和责任人正确隔离。
- 平台管理端可以查看和管理组织、额度、成员、Key 和审计。
- 组织禁用、启用、解散、成员移除、Key 批量操作、额度调整具备审计和重复提交保护。
- 个人账号现有能力保持兼容，不因组织功能引入行为变化。

### 2.3 产品取舍原则

由于组织功能尚未上线，后续交付遵循以下优先级：

1. 组织角色、权限、计费、审计和数据隔离的产品语义优先。
2. 线上个人账号既有能力必须保持兼容。
3. 对当前分支尚未上线的组织中间态行为，不做产品兼容承诺。
4. 用户体验应优先保证可理解、可恢复、可追踪，避免把内部实现差异暴露给终端用户。
5. 技术实现应服务于产品语义，具体落地方式由技术方案承接。

## 3. 现状与差距摘要

### 3.1 当前状态

当前分支已经具备一版组织功能雏形，包括组织、成员、邀请、组织 Key、组织审计、组织额度、组织日志/任务归属以及部分平台管理入口。

但该能力尚未正式上线，也尚未形成对外产品承诺。因此，一期交付应以本文定义的目标体验和业务规则为准，当前实现仅作为复用参考。

### 3.2 主要产品差距

| 差距 | 当前表现 | 产品影响 |
|---|---|---|
| 组织所有权不完整 | 当前以 admin/member 为主，缺少明确 owner。 | 无法清晰表达组织最终责任人、所有权转交和解散权限。 |
| 默认额度策略不安全 | 新组织可能默认拥有可消费额度。 | 正式环境可能产生未授权或不可控消费。 |
| 账户上下文不够明确 | 个人空间与组织空间切换和请求归属仍需统一。 | 多窗口、多设备或异常状态下可能出现资源串用。 |
| 邀请安全需加强 | 邀请凭证生命周期和重发语义需规范。 | 邀请链接泄漏、重复邀请和撤销体验存在风险。 |
| 组织计费闭环不足 | 组织消费、退款、重试和异常修复仍需补齐。 | 可能出现多扣、少扣、重复扣费或账务不可追溯。 |
| 高风险操作保护不足 | 批量 Key、额度调整、解散、成员移除等操作需具备重试保护。 | 用户重复提交或网络重试可能导致重复执行。 |
| 组织状态体验需统一 | disabled/dissolved 后的可见性、只读和恢复入口需明确。 | 用户和平台管理员可能看到不一致的组织状态。 |
| 审计脱敏需完善 | 高风险操作和敏感信息展示边界需明确。 | Key、邀请凭证、Prompt/Response 等敏感内容可能被误记录。 |
| 平台治理闭环不足 | 平台侧组织状态、成员、额度、Key、审计管理需完善。 | 运营、风控和客服无法完整处理组织问题。 |

### 3.3 现有能力处理原则

- 符合目标产品语义的现有能力可以复用。
- 与目标角色、权限、计费、审计或数据隔离规则冲突的中间态行为不作为兼容承诺。
- 面向线上用户的个人账号既有能力必须保持兼容。
- 组织功能上线前应完成必要重整，避免把未上线的临时行为固化为正式产品能力。
- 具体工程改造和迁移策略由技术方案承接。

## 4. 产品范围

### 4.1 一期范围

一期应覆盖完整组织闭环：

- Account Context：个人/组织账户上下文切换。
- 组织生命周期：创建、详情、更新、禁用、启用、解散、平台只读历史查看。
- 组织角色：owner/admin/member。
- 成员管理：列表、邀请、更新、移除、退出、所有权转交；普通组织侧不支持直接添加。
- 邮箱邀请：创建、重发、撤销、接受、过期处理。
- 组织 Key：单个/批量创建、列表、更新、删除、批量删除、责任人转交、visibility。
- Relay：组织 Key 鉴权、组织额度和 Key 限额双重约束。
- 组织计费：预扣、结算、退款、修复、额度流水。
- 日志与任务：组织 scope、责任人过滤、历史只读。
- 审计：高风险动作审计和敏感字段脱敏。
- 平台管理：组织列表、详情、状态、额度、成员、Key、日志、用量、审计。
- 前端组织中心：组织切换、组织详情、成员、邀请、Key、日志、用量与额度流水、任务、审计、设置。

### 4.2 一期不包含

以下能力不纳入一期：

- Project / 项目空间完整实现。
- 自定义角色。
- 服务账号 / 机器身份。
- SSO、SCIM、域名验证。
- 链接邀请、多次使用邀请。
- 组织独立充值订单、发票、订阅支付闭环。
- 成员硬性预算或成员额度分配。
- 个人与组织之间余额、订阅、历史日志、Key 的迁移。
- 组织日志完整 prompt/response 内容授权查看。
- 高级 Key 权限策略，如只读 Key、接口级权限、模型级策略之外的复杂 RBAC。

## 5. 核心概念

| 概念 | 定义 |
|---|---|
| 个人空间 | 用户个人使用 CubeRouter 的空间，个人 Key、日志、任务和额度归属于用户本人。 |
| 组织空间 | 多个成员共同协作的空间，组织 Key、日志、任务、用量和审计归属于组织。 |
| 账户上下文 | 用户当前正在使用个人空间还是某个组织空间。普通业务操作必须有明确上下文。 |
| 组织 Key | 归属于组织的 API Key，由组织额度结算，并按责任人归因。 |
| 责任人 | 当前对某个组织 Key 负责的组织成员，用于权限、归因和成员维度用量展示。 |
| 创建者 | 创建资源的用户。创建者不随责任人转交变化。 |
| 组织 Owner | 组织所有者，拥有组织生命周期和所有权治理的最高权限。 |
| Platform Admin | 平台管理员，仅在平台组织管理端及 `/api/admin/organizations/*` 处理组织运营和治理问题。 |
| Platform Root | 平台最高权限用户，仅在平台组织管理端及 `/api/admin/organizations/*` 执行 owner 修复、平台解散等极高风险动作。 |

## 6. 角色与权限

### 6.1 组织角色

一期组织内置三类角色：

- owner
- admin
- member

创建组织的用户默认成为 owner。owner 是组织生命周期和最终治理的核心角色。

### 6.2 Owner 规则

- 每个组织同一时间只能有一个 active owner。
- owner 可以管理 admin/member。
- owner 可以转交所有权。
- owner 可以解散组织。
- owner 不能被 admin 禁用、移除、降级。
- owner 不能直接退出组织，必须先转交所有权。
- owner 转交目标必须是本组织 active admin 或 active member。
- 转交成功后，新用户成为 owner，原 owner 自动降级为 admin。
- platform root 可在异常场景修复或转交 owner。
- platform admin 非 root 不能管理 owner。

### 6.3 权限矩阵

以下矩阵合并展示普通组织入口与平台组织管理入口，但两类角色不可跨入口提升：

- member/admin/owner 列适用于组织中心、`/api/organizations/*` 及其 `workspace`、`management`、`read_only` 访问模式。
- platform admin/root 列仅适用于平台组织管理及 `/api/admin/organizations/*` 的 `admin` 访问模式。
- platform admin/root 访问普通组织入口时必须是目标组织的 active member，且只按其 owner/admin/member 组织角色授权；无 membership 时拒绝，member 身份不会因平台角色获得提升。

| 能力 | member（普通入口） | admin（普通入口） | owner（普通入口） | platform admin（平台入口） | platform root（平台入口） |
|---|---:|---:|---:|---:|---:|
| 查看组织详情 | 是 | 是 | 是 | 是 | 是 |
| 更新组织名称/描述 | 否 | 是 | 是 | 是 | 是 |
| 修改组织 group | 否 | 否 | 否 | 是 | 是 |
| 禁用/启用组织 | 否 | 组织自禁用/自启用 | 组织自禁用/自启用 | 是 | 是 |
| 解散组织 | 否 | 否 | 是 | 否 | 是 |
| 查看成员列表 | 有限字段 | 是 | 是 | 是 | 是 |
| 邀请成员 | 否 | 是 | 是 | 否 | 否 |
| 直接添加成员 | 否 | 否 | 否 | 是 | 是 |
| 更新 admin/member | 否 | 受限 | 是 | 是 | 是 |
| 管理 owner | 否 | 否 | 仅转交 | 否 | 是 |
| 查看自己负责 Key | 是 | 是 | 是 | 是 | 是 |
| 查看全部组织 Key | 否 | 是 | 是 | 是 | 是 |
| 创建 private Key | 是 | 是 | 是 | 否 | 否 |
| 创建 public Key | 否 | 是 | 是 | 否 | 否 |
| 管理全部组织 Key | 否 | 是 | 是 | 是 | 是 |
| 查看自己日志/任务/用量 | 是 | 是 | 是 | 是 | 是 |
| 查看全组织日志/任务/用量 | 否 | 是 | 是 | 是 | 是 |
| 查看审计 | 否 | 是 | 是 | 是 | 是 |
| 调整组织额度 | 否 | 否 | 否 | 是 | 是 |
| owner 修复 | 否 | 否 | 否 | 否 | 是 |

### 6.4 权限展示原则

- 前端入口、按钮和危险操作必须由后端返回的权限能力驱动。
- 前端隐藏按钮不能作为安全边界。
- 平台管理端权限与组织成员权限必须独立判断。
- 组织中心不得根据全局 platform role 补充 capability；平台账号在组织中心只展示当前 active organization membership 对应的组织角色和能力。
- 权限不足时，应展示清晰、稳定、可定位的错误提示。

## 7. Account Context

### 7.1 产品要求

用户需要能明确区分当前操作发生在个人空间还是组织空间。

- 用户登录后默认进入个人空间，或进入上次保存的有效默认空间。
- 用户可以在个人空间和有权限访问的组织空间之间切换。
- 普通组织业务操作必须明确归属于某个组织空间。
- 当组织状态变化或成员权限失效时，系统应自动回退到个人空间，并给出可理解提示。
- 平台管理端不受用户当前空间影响。
- 组织 Key Relay 不依赖前端当前空间，而由 Key 自身归属决定结算和归因。

### 7.2 上下文列表与保存

需要提供：

- 可用个人/组织空间列表。
- 当前默认空间保存能力。
- 组织被禁用、解散或成员权限失效后的自动回退能力。

默认空间只用于前端初始化。每次业务操作仍必须重新校验用户当前是否有权访问对应空间。

### 7.3 回退规则

- 用户没有默认空间时进入个人空间。
- 默认组织已 disabled、dissolved 或成员不再 active 时，回退个人空间。
- disabled 组织不能进入可切换上下文，但可在组织管理入口展示。
- disabled 组织的普通管理/只读入口仅对 active owner/admin 展示；active member 没有进入 capability，platform admin/root 也不能凭平台角色进入普通入口。
- dissolved 组织不出现在上下文列表和普通组织列表中，仅 platform admin/root 可通过平台管理只读入口查看。

## 8. 组织生命周期

### 8.1 组织状态

组织状态包括：

| 状态 | 含义 |
|---|---|
| `active` | 正常可用，可进入组织上下文和使用组织 Key。 |
| `disabled` | 被禁用，不能进入组织上下文，组织 Key 不可 Relay。 |
| `dissolved` | 已解散，终态，只能历史只读。 |

### 8.2 组织创建

创建规则：

- 登录用户可以创建组织。
- 组织名称不能为空。
- 创建者成为 active owner。
- 每个组织同一时间只能有一个 active owner。
- 正式环境新组织默认不可直接消费，需要由平台配置或调整额度后可用。
- 创建组织必须写审计日志。

### 8.3 组织更新

- owner/admin 可更新组织名称、描述。
- platform admin/root 可更新名称、描述、group。
- 组织名称（name）为必填字段，更新时不可为空或纯空格；描述（description）可不填。
- platform admin/root 更新时必须填写原因（reason）。
- 组织成员不能修改 group。
- dissolved 组织不可更新。
- 更新必须写审计日志。

### 8.4 禁用与启用

禁用组织：

- owner/admin 可执行组织自禁用。
- platform admin/root 可执行平台禁用。
- 前端必须要求输入完整组织 slug，后端必须严格校验 slug 后才可禁用；组织名称、空值或错误 slug 均无效。
- 禁用必须展示来源、操作者、原因和时间。
- 禁用后组织 Key 立即不可用。
- 禁用后组织从可切换组织列表移除。
- 禁用必须写审计日志。

禁用来源规则：

- 组织禁用至少区分组织自禁用和平台禁用。
- 平台禁用优先级高于组织自禁用。
- 如果组织同时存在组织自禁用和平台禁用，必须先解除平台禁用，owner/admin 才可能继续处理组织自禁用。
- platform disabled 未解除前，owner/admin 不能自助启用组织。

启用组织：

- 组织自禁用只能由 owner/admin 或平台恢复。
- 平台禁用只能由 platform admin/root 恢复。
- 前端必须要求输入完整组织 slug，后端必须严格校验 slug 后才可启用；校验失败时组织状态、禁用记录、Key blocker 和审计均不得变化。
- 启用时只能恢复由本次组织禁用导致的系统禁用 Key。
- 手动禁用的 Key 不得被自动恢复。
- 启用必须写审计日志。

### 8.5 组织解散

解散规则：

- owner 可以解散组织。
- platform root 可以解散组织。
- admin 不能解散组织。
- platform admin 非 root 不能解散组织。
- 解散是不可逆终态。
- 前端必须二次确认，建议输入组织名称或 slug。

解散前必须检查 blockers：

- 进行中的异步任务或 Midjourney 任务。
- 未完成的组织账务处理。
- 进行中的 Key 批量操作。
- 进行中的成员移除、退出或 Key 处理（public 转交/private 删除）流程。

解散后：

- 组织状态变为 dissolved。
- 全部组织 Key 终态不可用。
- pending 邀请撤销。
- 新 Relay 鉴权立即拒绝。
- 写审计日志。

历史只读：

- dissolved 组织不再通过普通 Account Context 进入。
- dissolved 组织不提供用户侧历史组织列表或详情入口。
- platform admin/root 可通过平台管理端查看 dissolved 组织历史数据。
- owner/admin/member 不再有 dissolved 组织历史访问权。
- 不允许导出。
- 不允许新增、更新、转交、邀请、额度调整或 Relay 调用。

## 9. 成员管理

### 9.1 成员状态

成员状态包括：

- `active`：正常成员。
- `disabled`：暂时禁用，不能继续使用组织能力。
- `exited`：成员主动退出。
- `removed`：由具备权限的角色移除。

### 9.2 成员唯一性

- 同一用户在同一组织内只能有一个成员身份。
- 用户退出或被移除后再次加入，应恢复原成员身份记录，而不是产生多个并存身份。
- 同一用户可以加入多个组织。

### 9.3 成员列表

- 普通组织入口由 owner/admin 查看完整成员列表；平台 `/api/admin/organizations/*` 入口由 platform admin/root 查看完整成员列表。
- platform admin/root 通过普通组织入口访问时，仍按其真实 organization role 判断：organization member 只能查看有限成员列表，非成员拒绝访问。
- member 可以查看有限成员列表。
- member 仅可看到昵称、邮箱、角色等基础字段。
- member 列表不支持搜索、筛选、排序、导出。
- removed/exited 成员默认不展示。

### 9.4 邀请添加成员

- owner/admin 通过邮箱邀请成员。
- 邀请角色只能是 admin 或 member。
- 邀请不能创建 owner。
- owner 只能通过 owner 转交产生。
- 平台 admin/root 可以直接添加成员，但也不能直接制造多个 owner。

### 9.5 更新成员

- owner 可管理 admin/member。
- admin 可管理 member，并可将 member 提升为 admin；admin 不能降级、禁用、移除或以其他方式管理现有 admin，也不能管理 owner。
- platform admin 可管理 admin/member。
- platform root 可修复 owner。
- owner 不能通过普通成员更新被创建、移除或降级。
- active admin 实际降级为 member 时，必须先在同一事务中转移其负责的全部 public Key：请求显式目标优先，否则只使用 active owner；目标必须是平台启用且组织内 active 的 owner/admin。没有 public Key 时不校验转移目标。
- admin 降级不改变其 private Key 的 `user_id`、`responsible_user_id`、visibility 或状态；转移失败时角色和全部 Key 归属整体回滚，并写独立阻断审计。
- 成员更新必须写审计日志。

### 9.6 禁用、移除、退出与 Key 处理

成员禁用与成员关系终止采用不同的 Key 处理规则：

- **禁用成员**：其负责的全部未删除组织 Key（public/private）必须保留原责任人和业务数据，并通过 `member_disabled` system blocker 统一变为不可用；不得转移或删除 Key。重新启用成员时清除对应 blocker；没有其他 active blocker 的 Key 恢复禁用前状态，仍有其他 blocker 的 Key 继续禁用。
- **移除成员**：`public` Key 必须转交责任人才完成操作；请求可指定本组织 active owner/admin，未指定时只默认转交给 active owner，不得回退到其他 admin。没有合法目标时操作必须失败，并清晰展示阻塞原因。`private` Key 直接软删除（写 token delete 审计），不进行转交；历史日志、用量和审计仍可追溯到 masked key。
- **主动退出**：保持现有 public Key 转交、private Key 软删除规则。
- `member_disabled` 与 `user_platform_disabled` blocker 只在其 `ref_id` 仍是 Key 当前责任人且来源仍处于禁用状态时有效；责任人变化后由统一 reconcile 清除失效来源。manual、组织禁用和组织解散 blocker 不因责任人转移而清除。
- 移除成员必须填写原因（reason）。
- 成员禁用/启用、Key blocker 变化、Key 转交、Key 删除、成员移除和退出均必须写相应审计日志。

owner 不能被禁用、移除或退出，必须先完成所有权转交。

## 10. 邀请

### 10.1 邀请类型

一期只支持邮箱邀请：

- 邀请必须指定目标邮箱。
- 邀请角色只能为 admin 或 member。
- 默认有效期为 7 天，可由系统配置调整。
- 邀请邮件包含一次性邀请链接。

### 10.2 邀请凭证安全

邀请凭证必须满足：

- 邀请链接只能在创建或重复邀请/重发时生成并发送。
- 系统不得保存可直接使用的明文邀请凭证。
- 接受邀请时必须校验邀请凭证有效性。
- 审计日志不得保存明文邀请凭证。
- 重复邀请/重发必须生成新的邀请凭证，使旧邀请链接立即失效。
- 不允许新旧邀请链接同时有效。

### 10.3 邮箱匹配

- 创建邀请和接受邀请必须使用一致的邮箱规范化规则。
- 建议基础规则为去除首尾空格并转为小写。
- 接受邀请时，当前登录用户邮箱必须与邀请目标邮箱严格匹配。
- 不做 Gmail dot/plus、企业别名等邮箱供应商专属归一。

### 10.4 邀请状态

邀请状态包括：

- `pending`：待接受。
- `accepted`：已接受。
- `revoked`：已撤销。
- `expired`：已过期。

规则：

- 只有 pending 且未过期邀请可接受。
- disabled/dissolved 组织不能接受邀请。
- 接受邀请后创建或恢复成员身份。
- 撤销只允许 pending 邀请。
- 解散组织时 pending 邀请自动撤销。
- 邀请创建、重复邀请/重发、接受、撤销必须写审计日志。

## 11. 组织 API Key

### 11.1 Key 归属

组织 Key 必须具备清晰的产品归属：

- 归属于某个组织。
- 有创建者，用于记录谁创建了该 Key。
- 有责任人，用于权限判断、用量归因和成员维度展示。
- 有可见性，用于控制普通成员能否查看。
- 有独立额度和状态，用于控制该 Key 的可用性。

组织 Key 的计费账户始终是组织，不是责任人的个人账户。具体数据字段和兼容策略由技术方案定义。

### 11.2 Visibility

组织 Key visibility：

- `private`：仅责任人和具备管理权限的角色可见。
- `public`：组织内成员可见。

规则：

- member 可查看本组织全部 public Key，以及自己负责的 private Key。
- member 只能管理自己负责的 private Key。
- member 只能担任 private Key 的责任人。
- public Key 的责任人必须是组织 owner 或 admin；member 不能创建 public Key，也不能担任 public Key 责任人。
- owner/admin 可以管理本组织全部 Key。
- platform admin/root 可通过管理端查看、更新、删除、转交组织 Key，但默认不创建组织 Key。
- 组织 Key 完整 secret 在列表、详情、更新、转交等接口中按操作者权限每次返回，便于成员随时取用；同时附带 masked key 预览用于安全展示。

### 11.3 创建与批量创建

组织 Key 创建规则：

- 组织必须 active。
- 责任人必须是 active 成员。
- member 只能创建自己负责的 private Key。
- owner/admin 可指定 active 成员为责任人。
- group 必须在组织可用 group 范围内。
- 创建必须写审计日志。

批量创建规则：

- 必须具备重复提交保护。
- 必须 all-or-nothing。
- 任一 Key 的参数、责任人、group、额度或模型限制校验失败时整批失败。
- 首次成功与幂等重试均按操作者权限返回完整 secret，并同时返回 masked key 预览。
- 系统不得在重复提交保护记录中保存 Key secret。

### 11.4 更新、删除、批量删除、转交

- 更新可调整状态、额度、过期时间、模型限制、group、visibility、责任人等。
- member 不能更新他人 Key 或 public Key。
- owner/admin 可转交责任人。
- 删除应保留必要历史记录，避免影响审计、用量和账务追溯。
- 批量删除必须具备重复提交保护。
- 批量删除必须 all-or-nothing。
- 任一 Key 不属于本组织、不可见、已删除或不可删除时整批失败。
- 更新、删除、转交、批量操作必须写审计日志。
- 影响 Key 鉴权结果的操作必须及时使已缓存的鉴权结果失效。

### 11.5 系统禁用

组织状态、成员状态或其他系统原因导致 Key 不可用时，Key 必须能展示清晰的不可用原因，并支持多原因并存。

系统禁用至少需要表达：

- 组织自禁用。
- 平台禁用组织。
- 成员被禁用。
- 组织已解散。

恢复规则：

- 解除某一系统原因时，只解除对应不可用原因，不直接恢复 Key。
- 只有不存在其他不可用原因，且 Key 原状态允许恢复时，才允许恢复。
- 手动禁用 Key 不自动恢复。
- 组织已解散是终态原因，不允许恢复。
- 系统不可用原因变化后，Key 鉴权结果必须及时失效。

## 12. Relay、额度与计费

### 12.1 Relay 鉴权

组织 Key Relay 时必须校验：

- Key 可用且未过期。
- Key 属于有效组织。
- 组织处于 active 状态。
- Key 责任人是 active 成员。
- Key group 在组织可用 group 范围内。
- Key 自身额度满足要求，除非该 Key 不受额度限制。
- 组织可用额度满足要求。

Relay 产生的日志、任务、用量和账务必须能追溯到组织、Key、创建者、责任人和具体请求。

组织 API Key 在 `TokenAuth` / `relay_auth` 阶段失败时，请求尚未进入 Relay 执行，不写组织审计日志，也不写普通 Relay 日志；鉴权状态码和错误响应保持原语义。

### 12.2 组织额度规则

正式环境新组织默认不可直接消费，需要由平台配置或调整额度后才可用。

组织消费时：

- 只增加组织用量。
- 只扣减组织可用额度和对应组织 Key 限额。
- 保留 channel 维度用量统计。
- 不改变责任人的个人额度或个人用量。
- 不使用责任人的个人订阅、钱包或 trust quota。

### 12.3 计费闭环

组织计费必须支持请求级追踪和不可变流水，确保每次组织消费可结算、可退款、可修复、可审计。

要求：

- 预扣、结算、退款必须具备重复提交保护。
- 同一请求或任务不能重复扣费。
- 退款不能重复恢复组织额度或 Key 额度。
- 组织额度和 Key 额度必须保持一致。
- 异常中断后，系统应能通过后台修复流程恢复到正确账务状态。
- 解散组织前必须检查是否仍有未完成账务处理。
- 具体计费会话、流水和状态机设计由技术方案定义。

### 12.4 异步任务计费

组织场景下的异步任务和 Midjourney 任务必须保存足够的组织归属和计费归因信息。

规则：

- 成功回调只结算一次。
- 失败、取消或超时应按规则退款。
- 异步任务的计费、日志和用量展示必须与 Relay 同步请求保持同一套组织归属语义。
- 任务完成前如组织被禁用或解散，不得产生新的组织消费。

## 13. 用量、日志与任务

### 13.1 日志归属

组织消费日志必须具备清晰的组织归属和责任归因，至少能支持按以下维度展示和筛选：

- 组织。
- 责任人。
- 创建者。
- Key。
- group。
- 请求或任务。

在独立日志库场景下，日志展示仍应可用，不应依赖实时关联主库才能展示必要的组织、用户和 Key 摘要信息。

### 13.2 日志可见性

- 普通组织入口由 owner/admin 查看全组织日志；平台 `/api/admin/organizations/*` 入口由 platform admin/root 查看全组织日志。
- platform admin/root 通过普通组织入口访问时，仍按其真实 organization role 判断：organization member 只能查看自己负责的日志，非成员拒绝访问。
- member 只能查看自己负责的日志。
- 日志列表默认不返回完整 content。
- 查询和导出必须复用同一权限过滤。
- dissolved 组织不允许导出。

### 13.3 任务可见性

- 个人任务列表不得混入组织任务。
- 组织任务列表 owner/admin 可看全组织。
- member 只能看本人负责范围内的任务。
- Task/Midjourney 的 fetch、batch fetch、change、remix 和 image seed 必须按当前操作者的 `user_id + scope_type + scope_id + billing_account_type + billing_account_id + organization_id` 隔离；仅知道任务 ID 不能跨空间读取或操作。

### 13.4 用量与额度流水

一期前端命名应使用“用量与额度流水”，避免误解为已支持组织支付账单、充值、发票或订阅。

需要展示：

- 组织总额度。
- 已用额度。
- 可用额度。
- 当月净消费。
- Key 数量。
- 成员维度消费。
- 月度趋势。
- 额度流水明细。

额度流水明细按余额变化展示：预扣、结算差额、退款和额度调整分别成行。请求失败时消费日志费用为 0，但额度流水仍保留等额的预扣与退款记录，便于审计完整余额变化。

月度口径：

- 成功结算进入结算月份。
- 退款进入退款发生月份。
- 当月净消费等于已结算消费减去已退款消费。
- 纯预扣及其释放不计入消费、请求数、活跃用户或使用中的 Key。
- 额度调整只影响额度流水展示，不计入模型消费。
- 月份边界由应用时区计算为 Unix `[month_start, next_month_start)` 半开区间，禁止依赖数据库 session timezone 或数据库方言的日期转换。
- 历史数据不回填无法准确恢复快照的预扣流水；历史纯预扣退款通过查询兼容排除，已有 settle 的退款继续按净消费统计。

## 14. 审计

### 14.1 审计范围

以下动作必须审计：

- 创建组织。
- 更新组织。
- 禁用/启用组织。
- 解散组织。
- 调整组织额度。
- 添加、邀请、更新、禁用、移除、退出成员。
- owner 转交或修复。
- 成员 Key 处理（禁用时 system blocker 保留并恢复原状态；移除/退出时 public 转交、private 软删除、无合法 public 转交目标 blockers）。
- 成员 Key 转交被 blocker 回滚、Billing 后台修复失败等高风险失败路径；失败审计不得改变原业务错误。
- 创建、重复邀请/重发、接受、撤销邀请。
- 创建、批量创建、更新、删除、批量删除、转交组织 Key。

### 14.2 审计内容

审计日志应能回答以下问题：

- 哪个组织发生了操作。
- 谁在什么角色下执行了操作。
- 操作类型是什么。
- 操作对象是什么。
- 操作前后关键业务状态有什么变化。
- 操作原因是什么。
- 操作发生的时间和必要访问来源信息是什么。

操作者角色必须与入口一致：组织中心和 `/api/organizations/*` 产生的审计记录 owner/admin/member 组织角色；平台组织管理和 `/api/admin/organizations/*` 产生的审计记录 platform_admin/platform_root 平台角色。重叠 membership 不得改变该口径。

具体内容结构、快照口径和保存方式由技术方案定义。

### 14.3 脱敏要求

审计不得记录：

- 完整 Key secret。
- 邀请明文凭证。
- 可用于还原敏感凭证的密文或中间值。
- 完整 prompt/response。
- 其他敏感凭证。

Key 审计只记录：

- 稳定 Key ID。对于单 Key 审计，`target_id` 是组织 Key 的唯一、不可变标识，用于精确区分同名或 preview 相近的 Key；批量转交等聚合事件记录数量和变更快照，不伪造单一 Key ID。
- Key 名称和 masked key preview。二者均为操作发生时的快照；preview 应保留足以由操作者区分 Key 的首尾字符，但不得包含完整 secret。
- 状态。
- 责任人。
- visibility。
- 变更字段。

审计列表、详情和导出均不得返回完整 Key secret，也不得在读取审计时从当前或已软删除的 Key 记录回填完整 secret。Key 被转交或删除后，审计仍使用原 `target_id`、名称和 masked preview 追溯该次操作。

邀请审计只记录：

- 规范化或脱敏邮箱。
- role。
- status。
- 过期时间。
- 邀请凭证的安全摘要，不记录明文凭证。

## 15. 重复提交保护

### 15.1 适用场景

以下高风险操作必须具备重复提交保护，确保用户刷新、重试、网络抖动或客户端重复请求时不会造成重复执行：

- 批量创建 Key。
- 批量删除 Key。
- 额度调整。
- 重复邀请/重发邀请。
- 成员移除或退出并触发 public Key 批量转交或 private Key 软删除。
- owner 转交。

### 15.2 产品行为

- 重复提交保护主要针对未确认的中间态（如网络中断、未收到响应）：用户重试同一高风险操作时，系统应返回同一处理结果或清晰提示正在处理中，避免重复扣费或重复创建。
- owner 转交等终态写操作首次成功即完成：转交成功后原 owner 已降级，重复同一请求因操作者不再是 owner 而被拒绝属于正确行为，不要求重试返回同一成功结果。
- 如果重复请求的关键内容发生变化，系统应拒绝执行并提示用户重新发起操作。
- 批量操作应具备明确的成功、失败或处理中状态，不允许出现用户无法判断结果的中间状态。
- 批量创建 Key 幂等重试时返回同一处理结果，并同样返回完整 secret；组织 Key 完整 secret 在列表、详情、更新、转交、批量幂等重试中均每次返回。
- 具体重复提交标识、请求校验和结果保存规则由技术方案定义。

## 16. 对外能力与接口原则

本节只定义产品层面的对外能力边界。具体契约、错误码和重复提交实现由技术方案定义。

### 16.1 通用原则

- 接口设计应保持资源化、稳定和一致，避免动作式命名造成长期维护成本。
- 组织相关列表应支持分页、搜索、状态筛选和时间范围筛选。
- 高风险写操作必须明确是否需要重复提交保护。
- 错误响应应包含稳定、可国际化、可被前端识别的错误码。
- 普通组织接口与平台管理接口必须隔离；平台管理接口不依赖用户当前 Account Context。
- `/api/organizations/*` 只按目标组织 active membership 授权，platform admin/root 无 membership 时必须拒绝，有 membership 时也只使用 owner/admin/member 组织角色和 capability。
- `/api/admin/organizations/*` 只按 platform admin/root 授权，重叠 organization membership 不得降级或替换平台 capability。
- 审计相关能力统一使用 `audit-logs` 命名。

### 16.2 Account Context 能力

- 用户可以获取自己可访问的个人/组织上下文列表。
- 用户可以保存默认上下文。
- 普通组织业务请求必须明确表达当前账户上下文。
- disabled 组织不作为可切换的组织工作区；dissolved 组织不出现在用户侧上下文列表。

### 16.3 组织生命周期能力

普通组织侧需要支持：

- 查看当前用户可访问的 active/disabled 组织。
- 创建组织。
- 查看组织详情。
- 更新组织名称、描述等基础信息。
- owner 解散组织，且必须进行二次确认。
- owner/admin 按权限禁用或恢复组织自禁用状态。
- owner 转交组织所有权。

产品约束：

- dissolved 组织不提供用户侧历史读取入口。
- 平台禁用的组织不能被 owner/admin 自行恢复。
- owner 转交目标必须是本组织 active 成员。

### 16.4 成员能力

普通组织侧需要支持：

- 查看成员列表。
- 邀请成员加入组织。
- 更新 admin/member 的角色或状态。
- 移除成员。
- 当前用户退出组织。

产品约束：

- 普通组织成员管理不提供“直接添加成员”；用户加入组织必须通过邮箱邀请接受流程完成。
- 平台 admin/root 如需直接添加成员，应在平台管理端完成。
- 禁用成员时，其负责的 public/private Key 保留责任人并通过 `member_disabled` blocker 暂时禁用，重新启用后按 blocker 规则恢复原状态。
- 移除或退出成员时，该成员负责的 public Key 必须转交责任人才完成操作（移除未指定目标时只使用 active owner；无合法目标则操作失败）；private Key 随成员操作软删除。

### 16.5 邀请能力

组织邀请需要支持：

- 创建邮箱邀请。
- 查看邀请列表。
- 对已有 pending 邀请进行重复邀请/重发。
- 查看邀请摘要。
- 登录用户接受邀请。
- 撤销邀请。

产品约束：

- 不提供单独的 resend 能力入口；重复邀请/重发作为“重新发送 pending 邀请”的同一业务能力表达。
- 重复邀请/重发必须更新邀请凭证，使旧邀请链接立即失效。
- 重复邀请/重发必须具备重复提交保护。
- 接受邀请是 token auth 例外：调用前不要求已有 organization membership；邀请校验成功并在同一事务落库 active membership 后，接受邀请审计按新组织角色和 `workspace` 访问模式记录。

### 16.6 Key 能力

组织 Key 需要支持：

- 创建单个 Key。
- 批量创建 Key。
- 查看 Key 列表和详情。
- 更新 Key 名称、状态、可见性、额度等信息。
- 删除单个 Key。
- 批量删除 Key。
- 转交 Key 责任人。

产品约束：

- 批量创建和批量删除必须具备重复提交保护。
- 组织 Key 完整 secret 在创建、列表、详情、更新、转交、批量幂等重试等接口中按操作者权限每次返回，masked key 预览用于安全展示。
- member 只能管理自己负责且有权限可见的 Key。
- owner/admin 可以按权限管理组织内 Key。

### 16.7 日志、任务、用量与审计能力

组织侧需要支持：

- 查看组织日志和统计。
- 查看组织任务和 Midjourney 任务。
- 查看组织用量、成员用量汇总、月度汇总和额度流水。
- 查看组织审计日志。

产品约束：

- active 组织按角色权限正常访问。
- disabled 组织只允许 owner/admin 通过管理入口进行只读查看，不允许写操作或导出。
- dissolved 组织不提供用户侧读取入口。
- member 只能查看自己负责范围内的日志、任务和用量，不能查看全组织审计。

### 16.8 平台管理能力

平台管理端需要支持：

- 查看 active/disabled/dissolved 组织列表和详情。
- 更新 active/disabled 组织基础信息和分组。
- 启用或禁用组织的平台治理状态。
- root 解散组织，且必须进行二次确认。
- root 转交或修复组织 owner。
- 创建组织额度调整流水。
- 查看全局组织审计和单组织审计。
- 查看和管理组织成员、组织 Key、日志、任务、用量和额度流水。

产品约束：

- 平台管理端不依赖用户当前 Account Context。
- dissolved 组织仅 platform admin/root 可通过平台管理端只读查看。
- dissolved 组织不允许写操作或导出。
- owner 修复和平台解散仅 root 可执行。

## 17. 前端范围

### 17.1 Account Context 切换

前端需要提供：

- 个人/组织切换器。
- 当前上下文持久化。
- 每次普通业务请求都能明确表达当前空间。
- 上下文切换后清空上下文敏感缓存，避免展示旧空间数据。
- 上下文失效时自动回退个人空间。

平台管理端请求不受当前 Account Context 影响。

### 17.2 组织中心

组织空间页面包括：

- 概览：额度、当月用量、请求数、成员数、活跃 Key、近期错误。
- 成员：成员列表、角色、状态、负责 Key 数、用量摘要。
- 邀请：创建、重复邀请/重发、撤销、状态筛选。
- Key：组织 Key 列表、创建、编辑、删除、转交、批量操作。
- 日志：组织消费日志和筛选统计。
- 用量与额度流水：摘要、成员汇总、月度趋势、流水明细。
- 任务/Midjourney：组织 scope 下任务。
- 审计：组织审计日志。
- 设置：名称、描述、状态、危险操作。

页面和按钮必须由服务端 capabilities 驱动。

组织中心只能消费普通组织入口返回的 owner/admin/member capability，不读取全局 platform role 做补充或回退。platform admin/root 只有在目标组织拥有 active membership 时才能进入，并严格使用该 membership 的组织角色。

### 17.3 Disabled / Dissolved 体验

- disabled 组织不能进入组织 workspace，也不能作为 Account Context。
- disabled 组织可进入独立管理入口，用于查看禁用原因和可用恢复动作。
- disabled 管理入口必须校验 owner/admin 身份和组织 disabled 状态。
- member 不具备 disabled 管理或只读入口 capability；platform admin/root 如需治理 disabled 组织必须进入平台组织管理端。
- disabled 管理入口展示禁用来源、原因、操作者和可用恢复动作。
- platform 禁用的组织不向 owner/admin 展示启用入口。
- dissolved 组织从上下文列表和普通组织列表移除。
- 用户侧不提供 dissolved 历史入口。
- 平台侧 dissolved 历史详情仅通过平台管理端查看。
- dissolved 组织不展示导出入口和任何写操作。

### 17.4 平台管理端

平台管理新增：

- 组织列表。
- 组织详情。
- 状态切换。
- 额度调整。
- 成员管理。
- Key 管理。
- 日志、任务、用量与额度流水、审计查看。
- owner 修复和解散组织仅 root 可见。

## 18. 数据与迁移要求

### 18.1 数据能力要求

一期需要满足以下数据能力：

- 组织必须有唯一、明确、可转交的 owner。
- 组织状态必须能区分 active、disabled、dissolved，并保留必要的操作者、原因和时间信息。
- 成员角色必须支持 owner/admin/member，并能表达 active、disabled、removed 等生命周期状态。
- 邀请必须只保存安全凭证，不保存可直接使用的明文邀请链接。
- 组织 Key 必须能表达归属组织、创建者、责任人、可见性、额度和系统禁用状态。
- 组织消费必须有可追踪的会话和流水，支持预扣、结算、退款和修复。
- 高风险操作必须有重复提交保护记录。
- 日志、任务、用量和审计必须能按组织、成员责任范围和平台管理视角查询。

### 18.2 兼容性要求

- 现有个人账号、个人 Key、个人日志、个人任务和个人计费行为必须保持兼容。
- 新增或调整的数据能力不得破坏 SQLite、MySQL、PostgreSQL 三类部署。
- 旧个人资源应在组织功能上线后仍默认归属个人空间。
- 组织功能上线前已有的中间态组织数据如无法自动满足 owner、状态、计费或审计要求，必须通过迁移或平台 root 修复流程处理。

### 18.3 迁移原则

- 迁移完成后，每个可用组织必须有且仅有一个 active owner。
- 无法可靠判断 owner 的组织，应进入平台修复流程，不应对普通用户暴露异常组织状态。
- 大规模历史数据迁移应避免影响线上个人功能可用性。
- 迁移过程应可回溯、可验证，并具备失败后的安全恢复策略。
- 具体迁移方案和多存储兼容方案由技术方案定义。

## 19. 安全要求

### 19.1 数据隔离

- 所有组织资源查询必须限定在明确组织范围内。
- member 只能访问自己有权限负责或可见的数据。
- 成员有限列表是例外，但不能返回管理敏感字段。
- 平台管理端必须显式校验 platform admin/root 权限。
- dissolved 组织不可导出。

### 19.2 Key 安全

- 组织 Key 完整 secret 在列表、详情、更新、转交等接口中按操作者权限每次返回，便于成员随时取用；masked key 预览用于安全展示。
- Key 删除、禁用、转交后，已缓存的鉴权结果必须及时失效。
- 组织禁用或解散后，组织 Key 必须立即不可用。

### 19.3 邀请安全

- 系统不保存邀请明文凭证。
- 邀请凭证必须足够随机，不能被猜测。
- 邀请凭证的安全摘要必须唯一。
- 接受邀请必须登录且邮箱严格匹配。

### 19.4 审计安全

- 审计日志不得包含完整敏感凭证。
- 审计日志不得由组织 owner/admin 修改或删除。
- 平台查询审计应保留完整操作人快照。

## 20. 分阶段交付建议

### Phase 1A：账户上下文与组织基础

目标：修正组织基础模型和权限语义，并交付可用的最小组织创建、切换、成员和邀请基础页面。

范围：

- 引入 owner 角色。
- 创建者成为 owner。
- 保证每个组织同一时间只有一个 active owner。
- 正式环境新组织默认不可直接消费。
- 个人空间与组织空间请求归属校验。
- disabled/dissolved 上下文回退。
- 成员 owner 保护和 owner 转交。
- 邀请凭证安全改造。

验收：

- 个人/组织上下文不串。
- owner 不能被 admin 移除、禁用、降级或直接退出。
- 组织创建后只有一个 active owner。
- 接受邀请邮箱严格匹配。

### Phase 1B：组织 Key 与可靠 Relay 计费

目标：使组织 Key 可安全 Relay，并只扣组织额度。组织 Key 一旦对正式用户开放 Relay，必须同时具备可靠计费闭环；前端交付组织 Key 和基础 Relay 状态的可用页面。

范围：

- 组织 Key 创建、批量创建、删除、批量删除、转交。
- visibility 权限。
- 多原因系统禁用展示。
- Key 鉴权结果失效。
- 组织 Key 鉴权。
- 组织消费请求级追踪和不可变流水。
- 组织额度和 Key 限额双重约束。
- 预扣、结算、退款、修复的最小可靠闭环。

交付约束：

- 如果 Phase 1B 未完成可靠计费闭环，则组织 Key Relay 只能内测或灰度验证，不允许作为正式可用能力对外发布。
- 正式发布组织 Key Relay 前，必须确保不存在绕过可靠计费闭环的旧扣费路径。
- Phase 1B 的账务能力可以只覆盖 Relay 同步/流式请求的最小闭环；异步任务、复杂用量报表和完整前端流水可以放到 Phase 1C。

验收：

- 组织 Key 调用不影响个人额度。
- 组织 disabled/dissolved 后 Key 立即不可用。
- member 不能管理他人 private Key。
- 批量创建/删除 all-or-nothing。
- 组织 Relay 预扣、结算、退款在重复请求下不会重复执行。
- 并发 Relay 不透支组织额度。

### Phase 1C：组织日志、任务、用量、审计

目标：补齐组织日志、异步任务、用量展示和审计可见性，并扩展 Phase 1B 已建立的可靠计费闭环；前端交付日志、任务、用量和审计的基础可用页面。

范围：

- 计费闭环支持异步任务、复杂退款和后台修复场景。
- 异步任务组织计费。
- 组织日志和任务归属查询。
- 用量与额度流水页面能力。
- 审计脱敏和高风险动作覆盖。

验收：

- 流式/非流式/异步任务只结算一次。
- 退款重复执行时不会重复恢复额度。
- 并发不透支组织额度。
- member 只能查看自己负责日志、任务和用量。
- 审计不含 Key secret 和邀请明文凭证。

### Phase 1D：平台管理端与前端组织中心

目标：完成组织中心产品化体验、平台管理端闭环和高风险管理流程。

范围：

- 组织中心页面。
- 平台组织管理页面。
- 额度调整。
- disabled/dissolved 管理体验。
- 平台 dissolved 组织只读入口。
- 高风险动作二次确认。
- capabilities 驱动前端可见性。

验收：

- owner/admin/member/platform admin/root 前端入口和按钮正确。
- 平台禁用组织不能被 owner/admin 自行启用。
- dissolved 组织只读且不可导出。
- 额度调整有审计和重复提交保护。

## 21. 验收标准

发布前必须满足：

- 组织创建者成为唯一 active owner。
- owner 保护、owner 转交和 platform root 修复通过验证。
- 正式环境组织默认不可直接消费。
- 个人空间与组织空间请求归属一致。
- 个人 Key、个人日志、个人额度、个人任务行为保持兼容。
- 组织 Key Relay 不扣个人额度。
- 组织额度、Key 额度预扣/结算/退款具备重复提交保护。
- 并发消费不能突破组织额度。
- 组织 disabled/dissolved 后，Key、邀请、上下文、Relay 行为符合状态定义。
- 解散前 blocker 检查有效。
- dissolved 组织只读权限符合定义，平台写操作统一返回 HTTP 410 和 `organization_dissolved`。
- member 不能查看全组织日志、用量、审计和他人 private Key。
- 邀请凭证不明文保存。
- 组织 Key 完整 secret 在列表、详情、更新、转交、批量幂等重试每次返回，masked key 预览用于展示。
- 批量 Key 操作 all-or-nothing 且具备重复提交保护。
- Key 状态、组织状态、责任人变化后，已缓存鉴权结果及时失效。
- 审计覆盖所有高风险动作且敏感字段脱敏；普通组织入口与平台组织管理入口严格隔离 platform role 和 organization membership，审计角色与实际入口一致。
- SQLite、MySQL、PostgreSQL 迁移和核心流程通过。
- 独立日志库场景可用。
- 前端组织中心和平台管理端按 capabilities 展示。

## 22. 测试建议

### 22.1 后端测试

- Account Context：缺省、personal、organization、组织标识不一致、disabled、dissolved、成员 removed。
- 组织生命周期：创建、默认额度、禁用、启用、解散 blocker、平台只读历史查看。

- 邀请：凭证安全、过期、撤销、邮箱严格匹配、重复邀请。
- Key：private/public、责任人、转交、批量创建、批量删除、完整 secret 每次返回、鉴权缓存失效。
- Relay：组织额度不足、Key 额度不足、组织 disabled/dissolved、责任人 disabled、退款。
- Billing：计费状态、重复提交冲突、并发预扣、结算差额、退款、后台修复。
- Task/Midjourney：组织归属、ID 读取/变更双向 scope 隔离、成功结算、失败退款、超时恢复。
- 日志/用量：member 过滤、owner/admin 全量、独立日志库。
- 审计：敏感字段脱敏、高风险动作覆盖、Key 转交 blocker 和 Billing repair failure 的原错误优先级。
- 授权入口矩阵：platform non-member/member/admin/owner 分别覆盖 workspace/management/read_only/admin，普通入口只使用组织角色，平台入口只使用平台角色。
- 邀请接受：token auth 例外、成员落库和 workspace 组织角色审计处于同一事务。
- 数据库矩阵：SQLite/MySQL/PostgreSQL。
- 并发与运行矩阵：额度调整、邀请接受、repair lease/batch continuation、Redis 关闭/开启。

### 22.2 前端测试

- Account Context 切换后请求归属正确。
- 上下文切换后不复用旧请求响应。
- disabled 管理页先读取详情，仅在收到 `organization_context_mismatch` 时切换 Account Context 并重试一次；其他错误不得触发隐式切换。
- member/admin/owner/platform admin/root 页面入口和按钮正确。
- 创建 Key 后完整 secret 在列表、详情每次可取用。
- 批量 Key 重复提交返回同一处理结果且每次含完整 secret。
- disabled 组织展示禁用原因并移除 workspace 入口。
- dissolved 组织只读且无导出。
- 邀请接受覆盖未登录、邮箱不匹配、过期、成功。
- 平台管理组织列表、详情、额度调整、状态切换、成员/Key 管理可用。

### 22.3 回归测试

- 个人 Key 创建、调用、扣费、日志不变。
- 个人任务和 Midjourney 不混入组织任务。
- 平台用户管理、渠道管理、模型倍率、订阅、充值、兑换码不受影响。
- 未启用缓存服务时组织功能仍可运行。
- 默认日志库和独立日志库两种模式均可运行。

| 主题 | PRD 决策 |
|---|---|
| 上线状态 | 组织功能以本文定义的一期目标为正式交付口径，不兼容当前分支尚未上线的中间态行为。 |
| 角色 | 一期必须引入 owner；创建者默认成为 owner；owner 是组织最终责任人。 |
| 默认额度 | 正式环境新建组织默认不可直接消费，需通过平台额度配置或调整后可用。 |
| Account Context | 用户必须能清晰区分个人空间和组织空间；普通组织业务请求必须有明确账户上下文。 |
| 邀请 | 成员加入以邮箱邀请为主；重复邀请/重发必须使旧链接失效。 |
| 成员添加 | 普通组织侧不支持直接添加成员；平台直接添加仅作为管理端能力。 |
| 组织 Key | 组织 Key 必须具备明确的组织归属、责任人、可见性和额度约束。 |
| 计费 | 组织 Key 消费只扣组织额度，不影响责任人的个人额度、订阅或余额。 |
| 批量操作 | 批量 Key、额度调整、owner 转交等高风险操作必须具备重复提交保护；owner 转交为终态操作，首次成功后即完成，重复提交不再保证返回同一成功结果。 |
| 状态 | disabled 与 dissolved 的用户可见性、只读范围、恢复入口和平台治理入口必须符合本文定义。 |
| 审计 | 高风险动作必须审计，敏感信息必须脱敏。 |
| 前端 | 组织中心和平台管理端的入口、按钮和危险操作必须由权限能力驱动。 |
| 技术落地 | 具体工程改造、接口契约、数据迁移细节由技术方案承接。 |

## 24. 后续增强方向

一期完成后可继续演进：

- Project / 项目空间。
- Service Account / 机器身份。
- 自定义角色。
- Key 细粒度权限。
- 组织预算预警。
- 成员额度分配。
- SSO / SCIM / 域名验证。
- 组织级安全策略，如强制 2FA、IP 白名单、Key 自动轮换。
- 组织充值、发票、订阅和支付闭环。
